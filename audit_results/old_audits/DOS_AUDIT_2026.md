## D3 — Spam Attack Cost Analysis

### Fee Model

```
fee = base_fee + weight_fee + length_fee
    = ExtrinsicBaseWeight × 1 + dispatch_weight × 1 + encoded_length × 1
```

With `IdentityFee<Balance>` for both `WeightToFee` and `LengthToFee`, weight (in picoseconds) maps 1:1 to fee (in base currency units). With `FeeMultiplierUpdate = ()`, the multiplier is a constant 1.0 regardless of block fullness.

### Parameters

| Parameter | Value |
|-----------|-------|
| ExtrinsicBaseWeight | ~125,000,000 ps (Substrate default from `with_sensible_defaults`) |
| Normal block capacity (ref_time) | 0.75 × 2 × 10¹² = 1.5 × 10¹² ps |
| Normal block capacity (length) | 0.75 × 5 MB = 3.75 MB |
| Blocks per hour | 600 |
| Blocks per day | 14,400 |

### Minimum Extrinsic Cost

A minimal `system.remark([])` extrinsic:
- Base fee: 125,000,000 base units
- Dispatch weight: ~10,000,000 base units (remark of 0 bytes)
- Length fee: ~100 base units (encoded tx ~100 bytes)
- **Total ≈ 135,000,000 base units ≈ 0.000135 DALLA**

### Block Saturation Cost

| Metric | Minimal Spam (remark) | Realistic Spam (balance transfer) |
|--------|----------------------|----------------------------------|
| Weight per tx | ~135,000,000 ps | ~325,000,000 ps |
| Max txns per block | ~11,111 | ~4,615 |
| **Cost per block** | **~1.5 DALLA** | **~1.5 DALLA** |
| **Cost per hour** | **~900 DALLA** | **~900 DALLA** |
| **Cost per 24 hours** | **~21,600 DALLA** | **~21,600 DALLA** |
| **Cost per voting period (12h)** | **~10,800 DALLA** | **~10,800 DALLA** |
| **Cost per governance motion (7d)** | **~151,200 DALLA** | **~151,200 DALLA** |

### Impact Assessment

Because `FeeMultiplierUpdate = ()`, the cost **never increases** regardless of sustained block fullness. A motivated attacker pays the same rate on hour 1 as hour 168.

At hypothetical token prices:
| DALLA Price | 1-Hour Cost | 24-Hour Cost | 7-Day Cost |
|-------------|-------------|--------------|------------|
| $0.01 | $9 | $216 | $1,512 |
| $0.10 | $90 | $2,160 | $15,120 |
| $1.00 | $900 | $21,600 | $151,200 |
| $10.00 | $9,000 | $216,000 | $1,512,000 |

At any token price below ~$1, complete chain saturation for a full governance motion period (7 days) costs under $151K — well within range of a motivated attacker.

## D5 — Detailed Findings

### DOS-001 [CRITICAL] — All Weight Functions Are Hand-Estimated

**Location**: All 17 `pallets/*/src/weights.rs` files + economy inline weights  
**Confidence**: [VERIFIED]

**Evidence** (staking/src/weights.rs excerpt):
```rust
fn join_validators() -> Weight {
    Weight::from_parts(40_000_000, 0)
        .saturating_add(T::DbWeight::get().reads(4))
        .saturating_add(T::DbWeight::get().writes(3))
}
fn distribute_rewards() -> Weight {
    Weight::from_parts(80_000_000, 0)
        .saturating_add(T::DbWeight::get().reads(5))
        .saturating_add(T::DbWeight::get().writes(5))
}
```

All 245 weight functions across 18 pallets use round numbers (`40_000_000`, `30_000_000`, `25_000_000`, `80_000_000`). Substrate's `frame-benchmarking` macro produces irregular numbers tied to actual hardware performance measurements (e.g., `34_721_493`). The uniform round numbers confirm these are hand-estimated placeholders, not benchmarked values.

**Impact**: The actual execution cost of every extrinsic is unknown. Weights may be over- or under-estimating true costs by orders of magnitude, allowing either (a) block stuffing at below-cost or (b) wasted block capacity from overcharging.

**Remediation**: Run `frame-benchmarking` for all 18 pallets (see D6).

### DOS-002 [CRITICAL] — `staking::distribute_rewards()` O(N) with Constant Weight

**Location**: `pallets/staking/src/lib.rs:950-970`, `pallets/staking/src/weights.rs`  
**Confidence**: [VERIFIED]

**Code** (`lib.rs:956-957`):
```rust
let max_validators = T::MaxValidators::get() as usize;
for (validator_id, validator_info) in Validators::<T>::iter().take(max_validators) {
    // Per validator: 1 ModelSubmissions read + 1 Currency::deposit_creating + 1 total_issuance read
}
```

**Weight** (`weights.rs`):
```rust
fn distribute_rewards() -> Weight {
    Weight::from_parts(80_000_000, 0)
        .saturating_add(T::DbWeight::get().reads(5))
        .saturating_add(T::DbWeight::get().writes(5))
}
```

**Attack scenario**: With `MaxValidators = 100`, a single `distribute_rewards` call executes ~100 storage reads + ~100 writes + 100 currency operations. The weight charges for 5 reads and 5 writes. The block producer absorbs 95% of the actual cost unpaid.

**Resource math**:
- Actual cost: ~100 reads × 25μs + ~100 writes × 100μs ≈ 12.5ms
- Charged cost: 5 reads + 5 writes ≈ 0.625ms
- **Undercharge factor: ~20×**

**Remediation**: Weight must be parameterized:
```rust
fn distribute_rewards() -> Weight {
    let v = T::MaxValidators::get() as u64;
    Weight::from_parts(80_000_000, 0)
        .saturating_add(T::DbWeight::get().reads(5 + v * 2))
        .saturating_add(T::DbWeight::get().writes(5 + v))
}
```
Then replace with actual benchmarked weights.

### DOS-003 [CRITICAL] — `governance::finalize_proposal()` O(N) with Constant Weight

**Location**: `pallets/governance/src/weights.rs`, `pallets/governance/src/lib.rs`  
**Confidence**: [VERIFIED]

The `finalize_proposal` extrinsic iterates over all votes for a proposal to tally results. The weight function is:
```rust
fn finalize_proposal() -> Weight {
    Weight::from_parts(50_000_000, 0)
        .saturating_add(T::DbWeight::get().reads(5))
        .saturating_add(T::DbWeight::get().writes(3))
}
```

A popular governance proposal could accumulate hundreds or thousands of votes. The finalization reads all votes but charges a fixed cost of 5 reads.

**Remediation**: Parameterize by max vote count or use incremental tallying across multiple blocks.

### DOS-004 [CRITICAL] — `claim_participation_reward` — 2,000 Storage Reads

**Location**: `pallets/governance/src/lib.rs:5570-5590`  
**Confidence**: [VERIFIED]

```rust
// Pattern A: Check up to 1000 proposal votes
(0..max_check).any(|pid| Votes::contains_key(pid, &claimer))
// where max_check = min(NextProposalId, 1000)

// Pattern B: Iterate up to 1000 proposals for proposer check
Proposals::iter().take(1_000).any(|(_, prop)| prop.proposer == claimer)
```

**Attack scenario**: Any KYC'd user can call `claim_participation_reward` repeatedly. Each call forces the node to perform up to **2,000 storage reads** (1,000 `contains_key` checks + 1,000 full proposal deserializations). The extrinsic weight is constant — the attacker pays a fixed fee for a variable, potentially enormous, I/O cost.

The code comment states "SECURITY: Bounded iteration prevents DoS" — but 1,000 iterations per call is **not a practical bound** for a user-callable extrinsic.

**Remediation**:
1. Track participation in a per-account flag or counter: `HasParticipated::<T>::insert(account, true);`
2. Remove the iteration-based participation check entirely
3. If iteration is unavoidable, reduce bound to ≤20 and parameterize the weight

### DOS-005 [CRITICAL] — Only 1/245 Weight Functions is Input-Proportional

**Location**: All `pallets/*/src/weights.rs`  
**Confidence**: [VERIFIED]

Of 245 weight functions across 18 pallets, only `payroll::batch_payment(n: u32)` accepts a parameter that scales with input size. All other extrinsics that accept variable-length inputs (`BoundedVec`, multi-hop trade routes, identity documents) use constant-weight declarations.

Examples of variable-input extrinsics with constant weight:
- `belizex::execute_multihop_trade` — accepts a route of variable hops
- `identity::register_identity` — accepts `BoundedVec` fields
- `identity::update_did_doc` — accepts `BoundedVec` document data

**Impact**: Attackers can submit maximum-length inputs while paying the same fee as minimum-length inputs.

### DOS-006 [HIGH] — `proof_size = u64::MAX`

**Location**: `runtime/src/lib.rs:124`  
**Confidence**: [VERIFIED]

```rust
Weight::from_parts(2u64 * WEIGHT_REF_TIME_PER_SECOND, u64::MAX),
```

The `proof_size` dimension of the two-dimensional weight system is set to its maximum possible value, effectively disabling storage proof size limits. This means:
- No upper bound on the number of storage reads per block
- The second dimension of Substrate's weight system provides zero DoS protection
- On a parachain, this would cause relay chain validation failure; on a solochain, it removes a defense layer

**Remediation**: See D7.

### DOS-007 [HIGH] — `FeeMultiplierUpdate = ()`

**Location**: `runtime/src/lib.rs:445`  
**Confidence**: [VERIFIED]

```rust
type FeeMultiplierUpdate = ();
```

The fee multiplier is fixed at 1.0 regardless of block fullness. During sustained spam attacks, fees remain constant — the attacker pays the same rate in hour 1 as in hour 168. On properly configured Substrate chains, `TargetedFeeAdjustment` exponentially increases fees when blocks exceed target fullness, making sustained spam progressively uneconomical.

Note: `TargetedFeeAdjustment` is already imported at `runtime/src/lib.rs:62` but not wired in.

**Remediation**: See D8.

### DOS-008 [HIGH] — `belizex::on_idle` Returns `Weight::zero()` After Work

**Location**: `pallets/belizex/src/lib.rs` (on_idle hook)  
**Confidence**: [VERIFIED]

The `on_idle` hook performs dev-seed initialization logic including multiple storage reads and writes, then returns `Weight::zero()`. This means:
- The block weight accounting does not reflect actual work done
- Other hooks/extrinsics may be scheduled in the same block as if this hook consumed nothing
- Over many blocks, cumulative unmetered weight could cause block production delays

**Remediation**: Track actual reads/writes and return a proportional weight:
```rust
fn on_idle(_n: BlockNumberFor<T>, remaining_weight: Weight) -> Weight {
    let needed = T::DbWeight::get().reads(3).saturating_add(T::DbWeight::get().writes(2));
    if remaining_weight.all_lt(needed) {
        return Weight::zero(); // Not enough budget
    }
    // ... do work ...
    needed // Return actual consumed weight
}
```

### DOS-009 [HIGH] — Zero `DispatchClass::Operational` Usage

**Location**: All `pallets/*/src/lib.rs`  
**Confidence**: [VERIFIED]

No custom pallet extrinsic uses `DispatchClass::Operational`. This means:
- **All governance extrinsics compete in the `Normal` dispatch class** with everyday transfers and spam
- During block saturation, governance proposals/votes/finalization can be entirely displaced
- Critical chain operations (validator management, oracle submissions, emergency actions) have no priority lane

Substrate reserves 25% of block capacity for `Operational` transactions. With zero usage of this class, that capacity is wasted.

**Remediation**: Add `#[pallet::weight((weight, DispatchClass::Operational))]` to:
- All governance proposal/vote/finalize extrinsics
- Staking join/leave/distribute extrinsics
- Oracle submission extrinsics
- Emergency/admin operations

### DOS-011 [HIGH] — `join_validators` Unbounded Backfill Iteration

**Location**: `pallets/staking/src/lib.rs:654`  
**Confidence**: [VERIFIED]

When `ValidatorCount` storage item is 0 (initial state or storage corruption), the code falls back to:
```rust
Validators::iter_keys().fold(0, |acc, _| acc + 1)
```

This iterates **all** validator keys in storage to reconstruct the count. The weight is constant. An attacker could exploit this if `ValidatorCount` is somehow reset to 0.

**Remediation**: Initialize `ValidatorCount` in genesis/migration. Add a defensive guard:
```rust
let count = ValidatorCount::<T>::get();
ensure!(count > 0, Error::<T>::SystemNotInitialized);
```

## D7 — `proof_size` Remediation

### Current (Vulnerable)
```rust
// runtime/src/lib.rs:124
Weight::from_parts(2u64 * WEIGHT_REF_TIME_PER_SECOND, u64::MAX),
```

### Recommended Fix
```rust
// Match proof_size to block length limit (5 MB)
Weight::from_parts(2u64 * WEIGHT_REF_TIME_PER_SECOND, 5 * 1024 * 1024),
```

### Rationale
- `5 * 1024 * 1024` (5 MB) matches the `BlockLength` limit, providing consistency
- Substrate pallet authors encode proof_size estimates in their weight functions
- With `u64::MAX`, the proof_size dimension provides zero protection
- On parachains, this value would need to match the relay chain's PoV limit (~5 MB)
- For a solochain, 5 MB is a reasonable starting point; adjust after benchmarking

### Prerequisites
After setting a real `proof_size` limit, **all weight functions must include non-zero proof_size values**. Currently, some weight functions have `proof_size = 0` in their `Weight::from_parts()` calls, which would be undercharged once the limit is enforced. This fix should be applied **after** benchmarking (D6) is complete, since benchmarks will generate correct proof_size values.

## Summary

BelizeChain has **zero benchmarked weight functions** across 245 extrinsic weight declarations in 18 pallets. The entire weight system is built on hand-estimated round numbers that bear no measured relationship to actual execution costs. Combined with `proof_size = u64::MAX`, `FeeMultiplierUpdate = ()`, and zero `DispatchClass::Operational` usage, the chain is trivially vulnerable to spam-based DoS and governance displacement attacks at costs as low as **$9-900/hour** depending on token price.

The most critical individual findings are the O(N) extrinsics (`distribute_rewards`, `finalize_proposal`, `claim_participation_reward`) that perform unbounded or excessive storage iteration while charging constant fees.

**Recommended immediate actions (in priority order)**:
1. Wire `TargetedFeeAdjustment` (D8) — quickest defense against sustained spam
2. Set `proof_size` to 5 MB (D7) — enables the second weight dimension
3. Add `DispatchClass::Operational` to governance/staking/oracle extrinsics (DOS-009)
4. Fix the 3 critical O(N) extrinsics with parameterized weights (DOS-002/003/004)
5. Run `frame-benchmarking` for all 18 pallets (D6) — replace all hand-estimated weights
